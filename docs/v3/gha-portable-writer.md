**Legacy Staging:** `bash scripts/setup-staging.sh` and `AIRINGCAL_STAGING_*` apply **only** to the existing historical isolated two-bucket environment (`airingcal-staging-checkpoint` + `airingcal-staging-public`). Its real-R2 generations 1–3, CAS/lease, rollback proof are in [#147](https://github.com/Skyline-Gazer/AiringCal/issues/147), not still pending. `AIRINGCAL_WRITER_ENABLED` gates Production; `AIRINGCAL_DEVELOPMENT_WRITER_ENABLED` gates Development, and Staging manual dispatch needs its own real freeze procedure.

## What runs

| Piece | Path |
| --- | --- |
| Workflow | `.github/workflows/portable-writer.yml` |
| Staging setup CLI | `scripts/setup-staging.sh` (`scripts/setup-staging-lib.mjs`) |
| Shell entry | `scripts/gha-portable-writer.sh` |
| Orchestrator | `apps/node-jobs/src/cli/gha-portable-writer.ts` (+ `-main.ts`) |
| Schedule | cron `0 20 * * *` UTC = **04:00 Asia/Shanghai** |
| Mode | Checkpoint self-judge (≥7 days since last successful **full** → full); `workflow_dispatch` may set `force_mode` |

Flow (C2/C4): acquire lease → restore SQLite checkpoint from **private** R2 → sync portable builder → **image publish gate** over every referenced hash (upload missing, reuse present, fail closed when a published object's content differs or an original is nowhere available) → upload checkpoint with CAS → renew lease → commit the Release pointer with CAS → expire the lease. Nothing becomes visible before the checkpoint succeeds. The gate verifies/upload originals first, then thumbs, with bounded concurrency (default 8, max 32) and `publish_images_progress` events every 25 objects; the staging job allows 90 minutes because a first publish mirrors ~2.7k objects. Failure → Bark (`BARK_URL`).

## Unified Environment Configuration (`AIRINGCAL_{ENVIRONMENT}_{SERVICE}_{KEY}`)

All GitHub Actions Environment settings follow `AIRINGCAL_{ENVIRONMENT}_{SERVICE}_{KEY}` (`STAGING` legacy, `DEVELOPMENT` target, `PRODUCTION` gated). Checkpoint and Public buckets share a single scoped S3 credential pair per environment; non-sensitive infrastructure values (`CLOUDFLARE_ACCOUNT_ID`, `S3_ENDPOINT`, `S3_REGION`, bucket names, Worker name, `PUBLIC_BASE_URL`) are Variables or automatically derived in the workflow — never Secrets.

### Legacy Staging initialization (historical / rollback only; not new Development)

> Note: `.env.example` now documents the unified `AIRINGCAL_ENV` deploy contract (see `scripts/deploy-env.mjs`). For the one-shot staging flow below, add the `AIRINGCAL_STAGING_*` keys by hand; they remain valid and are listed as backward aliases at the bottom of `.env.example`.
Copy `.env.example` to `.env` (git-ignored) and fill in the 4 required keys (`AIRINGCAL_STAGING_BANGUMI_TOKEN`, `AIRINGCAL_STAGING_PRIMARY_USER_ID`, `AIRINGCAL_STAGING_S3_ACCESS_KEY_ID`, `AIRINGCAL_STAGING_S3_SECRET_ACCESS_KEY`), then run:

```bash
bash scripts/setup-staging.sh
```

`scripts/setup-staging.sh` safely parses `.env` without shell evaluation, queries the Bangumi API (`/v0/users/{username}` with `/v0/me` fallback) to resolve the real `userId` and `username` into `AIRINGCAL_STAGING_USERS_JSON`, verifies that `airingcal-staging-checkpoint` has `r2.dev` public access disabled, enables `r2.dev` HTTPS on `airingcal-staging-public`, syncs GitHub `staging` Variables/Secrets, and deploys `airing-cal-v3-read-staging` with `--env-file /dev/null`.

Wrangler authentication (`AIRINGCAL_STAGING_CLOUDFLARE_API_TOKEN` in `.env`, shell `CLOUDFLARE_API_TOKEN`, or `wrangler login`) must permit bucket administration and Worker deployment on the target account. The setup requires `Workers R2 Storage Write` to create buckets and change `r2.dev` access, plus `Workers Scripts Write` for deployment. The writer's scoped S3 credentials need Object Read & Write on both staging buckets; these object permissions alone do not authorize the Cloudflare REST bucket-management API. See [R2 authentication and permissions](https://developers.cloudflare.com/r2/api/tokens/).

If authentication succeeds but the R2 preflight reports `Authentication error [code: 10000]`, check the token's R2 management permission and account scope before retrying. A successful `whoami` does not prove R2 authorization. All setup Wrangler calls place `--env-file /dev/null` after the subcommand (for example, `wrangler whoami --json --env-file /dev/null`); placing it before the subcommand caused `Unknown argument: json` with Wrangler 4.100.0.

## Smoke

1. Run `bash scripts/setup-staging.sh` to provision/reuse the two staging buckets, enable public HTTPS on `airingcal-staging-public`, configure the `staging` Environment Variables + 3 Secrets, and deploy the staging read Worker.
2. Actions → **Portable writer (GHA)** → `workflow_dispatch` (`target=staging`, optional `force_mode=full`).
3. Expect job exit 0, `checkpoint_restore` / `gha_portable_writer_tick` / `checkpoint_upload` log events, checkpoint object `checkpoints/builder.sqlite`, public pointer `public/current-release.json`, and Bark silent on success. The built entry is `dist/portable-bundle/gha-portable-writer.mjs`; an exit 0 without Writer events or R2 artifacts is not a successful publish.

## Development single-bucket cutover (`AIRINGCAL_ENV=development`)

PR-D replaces the dual staging-bucket layout with **one** Development bucket
`airingcal-development` via `scripts/deploy-env.mjs` (driven by `.env` +
`AIRINGCAL_ENV` / `AIRINGCAL_DEPLOY_TARGET`). Key prefixes:

| Prefix | Visibility |
| --- | --- |
| `checkpoints/**` | Private — must be unreachable on the public custom domain |
| `public/**`, `snapshots/**`, `images/**` | Public via custom domain CDN |

Staging buckets (`airingcal-staging-checkpoint` / `airingcal-staging-public`)
remain as copy sources and are **not** deleted in this change. Production stays
frozen (`AIRINGCAL_WRITER_ENABLED` unset/false).

EdgeOne readers deploy to a new overseas project
`airingcal-edgeone-read-overseas` (`AIRINGCAL_EDGEONE_REGION=overseas`); keep
`airingcal-edgeone-read` until domain cutover acceptance.

**Image CDN off by default:** leave `AIRINGCAL_IMAGE_BASE_URL` unset so reader
`/image/*` redirects reuse `AIRINGCAL_PUBLIC_BASE_URL`
(`imageBaseUrl ?? publicBaseUrl`). When set, deploy validates https, rejects
same-host loops, and requires origin Host/SNI = public R2 host.

**Isolation abort (hard gate):** disable `r2.dev`, attach the custom domain, write
only `checkpoints/_isolation-probe.txt`, then prove anonymous GET/HEAD return
403/404 on every public entrypoint **before** copying real checkpoints. Failure
aborts cutover with a non-zero exit — no silent dual-bucket fallback; staging
readers stay active and the writer freeze remains until isolation passes.
Live I/O adapters are implemented (Code Complete → Live Deployment Ready).
`--apply` + credentials + `AIRINGCAL_DEPLOY_LIVE_CONFIRM=yes` mutate platforms;
without confirm/credentials the CLI refuses mutations. Isolation failure still
aborts before copy — do **not** treat a non-zero abort as dual-bucket success.

Workflow `inputs.target` gains `development` (Environment `development` +
`AIRINGCAL_DEVELOPMENT_*`). Until isolation+copy succeed, the development writer
job stays disabled so only one effective writer can run.

Reader-domain cutover (parity → CNAME `test.air.teijp.cn` → disable `r2.dev`) is
the Owner-executed follow-on to the `--apply` above:
[`reader-delivery-cutover.md`](./reader-delivery-cutover.md). Until its checklist
reaches `done`, the overseas EdgeOne project is live only as a preview and
`test.air.teijp.cn` still serves the global project.
